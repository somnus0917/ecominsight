### 5.1 店铺日报

四家抖音店铺的有效观察数分别是 11、39、43、12；各自在首末日期之间分别缺 1、7、3、8 天。只有两家接近 40 个观察，另两家不足两周。

- JSON 内共 130 个采集结果；

- 其中 23 行来自重复采集；

因此 Phase 2 应以 `luopan.db` 为权威源，并保留“文件与主库对账”测试。

### 5.2 渠道、商品与搜索

渠道只有 7 个采集日期：7 月 19、20、21、22、23、24、26 日，缺 7 月 25 日。每日店铺覆盖从 4、4、4 降为 3、3、1，再恢复为 4。23 个渠道店铺日全部能通过 `(shop_id, date)` 直接关联到经营日报。

商品 186 行包含 60 个店铺商品，搜索 362 行包含：

- `industry_term` 115 行；
- `shop_term` 115 行；
- `source` 132 行。

搜索表的空值必须按 `kind` 解释：

- 行业词的 `pay_amt`、`show_ucnt` 全空，但有排名、变化率和行业上下限；

把这些结构性空值汇总成全表“缺失率”会产生误导，需使用 kind-specific Pydantic 模型。

### 5.3 库存

最新库存包含：

- 1200 个仓库规格行；
- 46 个仓库、8 个品牌、969 个商品编码、969 个规格编码；

需要业务确认的质量问题：

- 28 行可用库存为负；
- 449 行可用库存小于等于 0；
- 81 行规格名为空字符串；

`lock_num` 全为 0，说明 WMS 可能存在未导出的占用、待审或在途口径。负库存不能直接当作解析错误，也不能与 0 库存合并。

### 5.5 结算

4 个文件共有 6202 个物理行。每个文件有 1 个无订单号和子订单号的汇总行，因此权威业务行是 6198 行，不是约 6210 行。

- 46 列，4 个文件 schema 一致；

- `luopan.db` 中金额字段为分，原始“元”值乘 100 后入库；

- `refund_amt`、`refund_amt_pay_time`、`deal_refund_amt_pay_time` 的统计时间和业务含义不同；

## 9. 隐私和商业敏感风险

### Critical

1. 订单全部含姓名、电话、详细地址和原始订单标识。
2. 快照含浏览器会话、认证表、登录截图、配置和运行日志。
3. `shop_name`、商户主体、商品名称、SKU 编码、达人信息和商品图片 URL 属于商业敏感数据。

### 强制控制

- 原始订单适配器必须流式处理：读一行，立即删除姓名/电话/地址，订单号和子订单号用外部盐做 HMAC，随后才允许构建 DataFrame；
- 店铺名称只保留 `Shop_A` 等稳定匿名名，映射存储在 Git 之外；
- 商品公开数据使用合成名；内部编码在演示导出前重新映射；
- 原始金额不进入公开演示数据；
- 日志只记录行数、字段、匿名实体 ID 和错误类别；
- 外部 LLM 默认关闭，只能接收聚合后、脱敏且经过证据校验的 JSON；
- CI 对演示数据和测试夹具扫描手机号、身份证、详细地址、原始订单号、Cookie、Token 和 Authorization；
- 发现敏感路径时应 fail closed，而不是“尽量跳过”。

## 11. 可行与暂不适合的算法任务

### 当前可完成

- 店铺支付金额、曝光、点击率、转化率、客单价的日环比、7/14 日滚动基线和 MAD/EWMA；
- 针对观察数达到阈值的两家店铺做 robust z-score / MAD 对比；
- 支付金额的对数变化分解：曝光、点击率、转化率、客单价；
- 7 日窗口内店铺到渠道、商品和搜索证据的直接关联；
- 商品横截面贡献、Top-N 集中度和单日异常贡献；
- 库存缺货、负可用库存、可售天数、低动销和积压规则；
- 结算流水的费用构成、符号校验、订单级聚合和异常费率；
- 合成异常注入和小型人工黄金集；
- 基于 SQL 证据和规则的归因，不依赖 LLM 计算核心指标。

### 当前不适合

- 对四家店统一启用 STL：序列过短、有缺日，且两家不足两周；
- 对商品/搜索/渠道做独立时序机器学习异常检测：每实体最多 7 个日期；
- 深度学习时序模型；
- 把缺失日期自动补 0 后训练模型；
- 在没有活动日、广告计划、价格变更和运营动作记录时声称因果；
- 用商品名称强行贯通商品、库存和结算；
- 仅凭 612 条两日订单评估长期订单异常；
- 在没有真实归因标签时宣称高准确率。

Isolation Forest 可在 Phase 4 作为 pooled baseline，但必须与规则/MAD 分开评测，不能把当前样本规模描述成充分。

## 12. 优先级最高的三个模块

1. **隐私闸门 + 可重复仓库构建**：先保证任何 PII、认证数据和重复测试导出都不能进入分析层。
2. **集中式指标注册表 + 店铺基线异常检测**：解决分/元、百分数/小数、支付/退款/结算多口径问题，并先覆盖最长的两条店铺序列。
3. **证据图和关联状态层**：用可靠的 `(shop_id, date)` 连接店铺、渠道、商品、搜索；库存/结算使用独立证据并显式标记未关联，避免伪归因。

## 13. 自动化质量测试建议

### 必须自动化

- 主键唯一：所有 SQLite 事实键、库存快照键；
- 权威订单路径 allowlist 与 test/session/config/log denylist；
- 订单脱敏后 PII 正则扫描；
- 金额单位转换：分到元精确除以 100；
- 比例范围和语义：比率 0～1，变化率允许超过 1；
- 结算汇总行排除；
- 渠道/商品/搜索父键完整性；
- 原始日报与主库店铺日对账；
- 演示数据 `synthetic=true`；
- 日志禁止敏感字段。

### 仅监控，不宜硬失败

- 每日行数与店铺覆盖；
- 负可用库存；
- 商品和搜索 payload 的可选字段；
- 结算费用的负号；
- 近期分区缺失，因为采集可能延迟。
