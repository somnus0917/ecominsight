# EcomInsight 求职材料

本文数字来自当前仓库的实际审计和本地流水线运行。受控场景评测与真实业务数据结果分开
陈述，不能把前者解释为线上业务准确率。

## 项目简介

EcomInsight 是一套多平台电商经营异常检测与证据归因系统。我将 SQLite、JSON、Excel
等异构经营数据治理为 Parquet + DuckDB 分析仓库，建立集中式指标、短时序异常检测、
指标分解和跨商品/渠道/库存/财务的证据规则，再通过本地检索与受约束结构化报告输出
可审计结论。FastAPI 和 React 控制台支持异常追踪与人工复核，默认不调用外部模型。

## 简历项目经历

- 设计多源电商分析仓库，审计并治理 165 条店铺日报、186 条商品日报、362 条搜索/来源
  记录、12,693 条库存快照明细、612 条订单及 6,198 条结算业务明细；订单在进入分析
  DataFrame 前完成删除与稳定匿名化。
- 建立固定阈值、Rolling Z-score、Rolling MAD 与 Isolation Forest 四类短时序基线；
  在 10 个受控异常场景上固定阈值 F1 为 0.758、场景召回 10/10，并完成恢复期误报和
  短窗口边界分析。
- 实现支付漏斗对数变化分解和十条确定性证据规则，将 296 条 detector-level 信号合并为
  277 个异常事件；受控场景 Rule Top-1 Accuracy 与 Candidate Recall 均为 1.000，
  Evidence Precision 为 0.750。
- 实现参数化 SQL 证据工具、本地 512 维 Hashing Embedding 和结构化报告校验；真实仓库
  生成 277 份报告、1,896 条声明，Unsupported Claim Count 为 0。
- 使用 FastAPI、React、TypeScript、TanStack Query 与 ECharts 交付 8 页经营控制台，
  将分析库设为只读并把人工反馈隔离到独立 SQLite，提供本地与 Docker Compose 运行方式。

## 1 分钟面试介绍

这个项目解决的不是“让大模型读 Excel”，而是电商经营异常的可验证分析。我先对真实
多平台数据做只读审计和隐私治理，再把店铺、商品、渠道、搜索、库存、订单和结算统一到
DuckDB。由于单店历史只有几十天，我没有上深度学习，而是比较固定阈值、Rolling Z、
MAD 和 Isolation Forest，并使用受控异常场景评测。检测之后，系统通过支付漏斗分解和
确定性规则收集证据，结构化数据只走 SQL，历史规则和案例才走本地检索。报告生成必须
引用 evidence ID，不能使用确定性因果措辞。最后我用 FastAPI 和 React 做了异常中心、
详情和人工复核。项目重点是数据口径、证据链、隐私和真实评测，而不是堆模型。

## 5 分钟技术介绍

1. **数据层**：源数据只读。发现器硬排除会话、凭证、截图和配置；订单适配器在构造
   DataFrame 前删除姓名、电话和详细地址，并用带盐 HMAC 匿名化业务标识。
2. **建模层**：各来源先进入独立 staging，再构建事实表、维度表和可确认桥接表。金额
   使用 `DECIMAL(18,2)` 元，比例保留 0～1，缺失日期不补零，不同统计口径不强行合并。
3. **指标与检测**：指标注册表集中保存公式、来源、粒度和空值策略。异常算法只使用历史
   窗口；固定阈值在强信号受控场景上优于复杂基线，Isolation Forest 用作交叉验证。
4. **归因层**：支付金额近似分解为曝光、点击率、转化率和客单价。十条规则显式声明
   前置条件、支持/反向证据和置信度；方向回归测试防止用下降因素解释上升事件。
5. **检索与报告**：数值不向量化，只用参数化 SQL。指标定义、规则和脱敏案例进入本地
   Hashing 向量索引。报告 Schema 校验 evidence ID、候选状态和因果措辞。
6. **应用层**：FastAPI 对 DuckDB 只读查询，React 控制台展示 8 个页面；人工反馈写入
   独立 SQLite。Docker 构建不包含原始快照，分析库只读挂载。
7. **评测边界**：真实数据没有完整标签，所以不报告真实 Precision/Recall。算法数字来自
   受控场景，真实结果只报告事件、证据和校验数量。

## 高频追问

### 为什么不用 LSTM 或 Transformer 做异常检测？

单店只有 11～43 个有效日报，复杂模型容易把噪声当模式，也无法可靠划分训练、验证和
测试集。当前采用可解释基线并设置历史门控；数据和标签积累后再比较更复杂模型。

### 为什么不用向量数据库存所有指标？

结构化数值需要精确过滤、聚合和可追溯公式，SQL 更合适。向量检索只处理指标口径、规则、
复盘和历史案例，避免近似检索替代精确计算。

### 如何避免大模型幻觉？

核心指标和归因候选先由程序计算。生成器只接收 EvidenceBundle；每条事实必须引用当前
证据 ID，报告落库前检查无来源声明和确定性因果措辞。默认生成器不依赖外部模型。

### Top-1 Accuracy 1.0 是否过高？

这是 10 个按规则覆盖设计的强信号受控场景，只证明规则实现和证据引用没有回归，不能
外推为真实生产准确率。真实归因仍需要人工标签和接受率评测。

### 为什么真实异常很多？

296 是 detector-level 候选信号，不是 296 个已确认业务事故。短历史、恢复期和稀疏日期
都会产生误报，系统合并后得到 277 个事件，并保留检测器和人工复核状态。

### 商品、库存和结算如何关联？

只使用已确认 ID 或标准编码。当前平台商品到 WMS、日报到结算流水没有可靠桥接，因此
系统保留数据不足说明，不按商品名称强行连接，也不输出库存或费用的确定性原因。

### 当前需要训练吗？

不需要离线训练。Isolation Forest 在历史窗口即时拟合，不保存训练权重；Hashing
Embedding 无需拟合。接入预训练 BGE 只需配置模型，真正微调要等人工确认案例足够后进行。

## 可公开与不可公开

可公开：

- 架构、数据模型、指标定义、算法代码、测试与评测方法；
- 脱敏截图、公开受控数据及聚合后的非敏感实验数字；
- 不包含业务身份的异常和报告示例。

不可公开：

- 原始数据库、订单和结算文件、真实店铺/商品/商户映射；
- 姓名、电话、地址、订单号及任何可反查消费者身份的信息；
- Cookie、Token、浏览器会话、登录截图、账号配置和密钥；
- HMAC 盐、脱敏映射、未经授权的真实经营明细。
